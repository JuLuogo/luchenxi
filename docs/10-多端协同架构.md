# 10 · 多端协同架构（v3）

> v2 是「教师端 localStorage 单写 + 服务器哑中继 + 大屏只读」。v3 把**学生小组端**接进来参与答题与抢答，
> 于是引入「教师机本地枢纽 + 房间 + 角色」。本文讲**为什么这样设计、数据怎么流、边界在哪**；
> 具体报文格式见 [07 通信协议与 API](07-通信协议与API.md)，部署与组网见 [08 开发部署与测试](08-开发部署与测试.md)。

## 1. 需求与三条硬约束

课堂现场要的是：老师推题 → 学生（小组）抢答/作答 → 立刻出结果并加分 → 大屏与学生端同步。

三条硬约束决定了架构：

| 约束 | 推论 |
| --- | --- |
| **不能依赖公网服务器**（课堂断网、不想备案/鉴权/运维） | 枢纽必须跑在**教师机本地**，教师端与学生端都连它 |
| 浏览器**无法监听端口**（学生端要连「教师端」） | 「教师端当服务器」落地为：教师机上跑一个随应用附带的 **Node 枢纽进程**，教师端页面用 `localhost` 连它 |
| 课堂需要**唯一权威**（同时两台设备写分数必然打架） | 教师端仍是**唯一写入者**；枢纽只做缓存/转发/广播；学生端是**无状态客户端** |

> 一句话：**浏览器当不了服务器，但教师机可以。** 学生手机访问的是 `http://<教师机IP>:8080/join`，
> 这个 IP 可以是局域网地址，也可以是 EasyTier 等组网工具分配的虚拟地址（界面会列出本机全部可用地址）。

## 2. 三端一枢纽

```
        ┌──────────────────────── 教师机（本地） ────────────────────────┐
        │                                                              │
        │   ┌──────────────┐        ┌──────────────────────────────┐   │
        │   │ admin.html   │        │  本地枢纽 sync-server.js      │   │
        │   │ 角色 = host  │◀──────▶│  · 静态托管（教师端/学生端/大屏）│   │
        │   │ 唯一写入者    │  WS    │  · 房间 + 角色 + 权威状态缓存   │   │
        │   │ localStorage │        │  · 命令转发 / 在线状态 / 二维码 │   │
        │   └──────────────┘        │  · 快照落盘 rooms/<房间>.json  │   │
        │          ▲                └───────────────┬──────────────┘   │
        │          │ 全量快照 state                 │                   │
        │          │ 完整数据 dump（仅教师端可读写）  │ 广播 state/cmd     │
        └──────────┼────────────────────────────────┼───────────────────┘
                   │                                │
                   │                     ┌──────────┴───────────┐
                   │                     ▼                      ▼
                   │            ┌────────────────┐    ┌──────────────────┐
                   └────────────│ index.html     │    │ student.html     │
                      （只读）    │ 角色 = stage   │    │ 角色 = team ×N   │
                                │ 教室大屏        │    │ 学生手机/平板     │
                                └────────────────┘    └──────────────────┘
```

| 端 | 角色 | 能不能改数据 | 主要职责 |
| --- | --- | --- | --- |
| `admin.html` | `host` | ✅ 唯一写入者 | 记分、组卷、点名、判分、课堂控制、学情分析；把全量快照推给枢纽 |
| `index.html` | `stage` | ❌ 只读 | 教室大屏：队伍榜、个人榜、当前题（含选项）、抢答榜、最近得分 |
| `student.html` | `team` | ❌ 只发命令 | 小组入座、抢答、提交答案、本组/个人看板；`?view=board` 变小组公屏 |

## 3. 一次「学生答题」的完整链路

以选择题为例（客观题自动判分）：

```
① 老师：在 ⑦ 课堂协同页推题 —— 「下一题 →」（或先在 ② 里选中某题）→ 「开始接收作答」（runtime.accepting = true）
        └─ 教师端 store 变更 → sync.push() → 枢纽缓存并广播 state（含当前题、选项、题目进度 questionIndex）
② 学生：手机端看到题目与选项 → 点选 → 「提交答案」
        └─ 发送 {type:'cmd', cmd:{kind:'answer', teamId, sid, qid, choice:['C']}}
③ 枢纽：把 cmd 转发给 host（教师端离线则进队列，上线补发 cmd-backlog）
④ 教师端：CI.classroom.handleCmd()
        ├─ 重复提交？→ 复用 answeredAlready() 判定，直接忽略
        ├─ CI.grade.auto(question, submission) → correct / half / wrong / skip
        ├─ store.recordResult({ source:'student', ... })  ← 与老师点名判分同一套加权公式
        └─ 写 classroom.feed（实时流）
⑤ 教师端：store 再次变更 → push() → 枢纽广播 → 学生端/大屏刷新
        └─ 学生端看到「答对 +3」；大屏个人榜/队伍榜即时变化
```

主观题走的是一条**人工回路**：`CI.grade.auto()` 对主观题返回 `null` → 提交进入 `state.classroom.pending`
→ 教师端「⑦ 课堂协同 → 待确认提交」点「答对 / 部分对 / 答错 / 跳过」→ 此时才 `recordResult({source:'student'})`。
**未判定前不产生任何流水**，因此不会污染学情统计。

## 4. 数据分区：什么存哪儿、为什么

| 数据 | 存放位置 | 理由 |
| --- | --- | --- |
| 名单、题库、试卷、积分流水、设置 | 教师端 `localStorage`（键 `ci_data_v2`）+ 枢纽 `rooms/<房间>.json` | 教师端是权威；枢纽缓存让大屏/学生端一连上就有数据，并让教师端换设备后能恢复 |
| `state.classroom = {pending, buzz, feed}` | 同上（随课堂数据持久化） | 抢答榜、待确认提交、实时流是课堂过程数据；持久化后**教师端刷新不丢待确认提交** |
| `runtime.accepting` / `runtime.reveal` / `runtime.revealedQid` | 同上 | 「是否接收作答」「是否公布答案」是课堂状态，学生端必须能看到；`revealedQid` 额外记住"公布的是哪一道题"，**换题即失效**，避免下一题的答案提前泄露到大屏与学生手机 |
| 在线小组 presence | **只在枢纽内存** | 是连接态而非业务数据；重启枢纽后由学生端重连自动重建 |
| 学生端的选择/输入 | 学生端内存 + `localStorage`（`ci_team` / `ci_answerer`） | 学生端无状态，刷新后重新入座即可，不影响成绩 |

**为什么学生端不存数据**：一旦学生端也持有课堂数据，就会出现两个真相来源（学生端断网改了、教师端又改了），
冲突合并的复杂度远超课堂收益。现在的模型里学生端**只发命令**，所有判定都在教师端发生。

## 5. 权威与容错

| 场景 | 行为 |
| --- | --- |
| 教师端刷新 / 换电脑 | 重连枢纽后自动请求 `dump`（完整课堂数据），若本机为空则提示「载入枢纽上的课堂数据」；否则以本机为准并覆盖枢纽 |
| 教师端短暂断线 | 学生端命令在枢纽排队（上限 60 条），教师端上线后补发 `cmd-backlog`，并提示「已补收 N 条离线提交」 |
| 学生端断线 | 页面每 1~8 秒自动重连；重连后重新 `hello` 入座，未提交的答案由学生自己重发（不排队到本地，避免重复计分） |
| 枢纽重启 | 从 `rooms/<房间>.json` 恢复快照与 dump，大屏/学生端一连上即有数据；presence 为空直到学生端重连 |
| 完全没有枢纽 | 教师端进入**单机模式**：记分、点名、组卷、学情全部可用，只是学生端与大屏收不到数据（顶部会提示） |
| 两台教师端同时打开 | **不支持**：后写者覆盖。课堂约定「一台机器记分，其它设备只看大屏」 |

## 6. 房间

- 房间号默认 `default`，在「⑦ 课堂协同」里可改（字母/数字/`-`/`_`，≤32 字符），学生端地址与二维码会随之更新。
- 用途：**多班同时上课**（同一台教师机、不同端口或不同房间）、**同一网络里跑多个班**避免串台。
- 学生端进房方式：扫二维码 / 直接输入 `http://<IP>:<端口>/join?room=<房间>`。
- 房间之间完全隔离：状态、命令、在线列表互不可见。

## 7. 组网（跨网段 / 不同 WiFi）

同一局域网（同一路由器）时学生直接访问教师机 IP 即可；跨网段、手机热点、校外访问时：

1. 教师机与学生设备都加入同一个 **EasyTier**（或 ZeroTier / Tailscale / WireGuard）虚拟网络；
2. 教师机执行 `ipconfig` 找到虚拟网卡地址（如 `10.126.0.1`）；
3. 教师端「⑦ 课堂协同」页会列出本机**全部可用地址**，把虚拟网地址那条发给学生（或换成该地址的二维码）；
4. 防火墙需放行该端口（Windows 首次运行 Node 时会弹窗，选「允许专用网络」即可）。

> 枢纽只监听 `0.0.0.0:<端口>`，不主动外联；**没有任何公网依赖**，所以「能不能连上」完全取决于学生设备能否路由到教师机。

## 8. 安全边界（课堂场景的取舍）

| 项 | 现状 | 说明 |
| --- | --- | --- |
| 鉴权 | **无** | 知道地址即可入座与提交。课堂内网可接受；公网暴露必须加反代鉴权 |
| 房间隔离 | 有 | 房间号是弱隔离（可猜），不做权限校验 |
| 学生端可提交他人？ | 可以（选任意队伍入座） | 以「队伍即身份」换取零登录成本；老师在大屏/协同页能看到每队入座与提交情况 |
| 篡改分数 | 学生端**无法**直接改分 | 学生端只能发命令，判定与计分全部发生在教师端 |
| 数据泄露 | 快照含全班姓名与分数 | `rooms/` 已加入 `.gitignore`；不要把 `rooms/`、`snapshot.json` 提交或公开 |
| HTTPS / WSS | 支持 | 若用反代提供 HTTPS，学生端地址自动用 `wss://`（同源判断） |

## 9. 与单机模式的兼容

- 教师端启动时若连不上枢纽，不影响任何本地功能（顶部提示「未连接枢纽（单机模式…）」）。
- 学生端/大屏在单机模式下无法获得数据 —— 这是唯一的功能差异。
- 一旦枢纽恢复，教师端会自动重连并推送当前状态，无需重启页面。
