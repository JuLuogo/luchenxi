## 1. 为什么要改，改成什么样

### 1.1 现状实测（排除依赖与生成物）

```
应用代码 21963 行：JavaScript 62.8% ｜ Vue SFC 22.3% ｜ Rust 10.2% ｜ TypeScript 0.0%
```

问题不在"架构错"，而在**职责划分**：

| 现在的样子 | 问题 |
| --- | --- |
| 业务规则写在 `assets/js/*.js`（判分、能力评价、点名、课堂环节…约 1.3 万行） | 无类型；同一份规则在 Node 枢纽、Rust 枢纽、三套前端之间**靠人肉保持同步** |
| Node 枢纽（`sync-server.js`）与 Rust 枢纽（`crates/ci-hub/src/lib.rs`）**两套实现** | 双份维护；只有 105 条一致性断言在挡漂移 |
| Rust 只有客户端壳 + 内嵌枢纽 | 真正的核心逻辑仍以 JS 为主 → 你说的"整个仓库以 JavaScript 为主" |
| 本机没有 Rust 工具链 | Rust 代码**只能在 CI 验证**，本地改动无法自测 |

### 1.2 目标

**一份核心逻辑（Rust），三端只做展示（Vue 3 + TypeScript）。** 类型由 Rust 生成，不再手写同步。

```
┌──────────────────────────────────────────────────────────────────────┐
│  展示层（只有渲染与输入，无业务规则）                                  │
│  Teacher UI (Vue3+TS)   Student UI (Vue3+TS)   Stage UI (Vue3+TS)     │
└───────────────▲──────────────────────▲───────────────────▲──────────┘
                │ invoke / events      │ HTTP + WS          │ HTTP + WS
                │（类型由 Rust 生成）   │                    │
┌───────────────┴──────────────────────┴───────────────────┴──────────┐
│  ci-core（facade：Tauri 命令与 HTTP/WS 路由，唯一对外面）              │
├──────────────────────────────────────────────────────────────────────┤
│  ci-hub        房间状态机 / 同步 rev / 409 过期写入 / 快照广播         │
│  ci-store      SQLite（rusqlite）：schema.sql + 迁移 + 备份/恢复       │
│  ci-domain     纯规则：加权计分 / 题型 / 能力评价 / 点名 / 课堂环节    │
│  ci-protocol   协议类型（由 packages/protocol 的 JSON Schema 生成）    │
└──────────────────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │ 内嵌（in-process）                  │ 独立进程（可选：教室大屏/多班级）
   apps/*/src-tauri（Tauri 薄壳）        hub 服务器模式（同一个 crate）
```

### 1.3 与成熟产品对照（为什么这么定）

| 产品 | 做法 | 我们的对应 |
| --- | --- | --- |
| **希沃白板** | 客户端壳 + 内部页面本身是网页（[社区实测](https://forum.smart-teach.cn/d/861-yi-fang-ni-bu-zhi-dao-xi-wo-bai-ban-de-zhe-xie-ye-mian-qi-shi-ye-shi-wang-ye/4)） | Tauri 壳 + Vue 页面（与希沃同构） |
| **ClassDojo** | 网页端 Node/React，移动端 React Native，业务逻辑集中在一处（[工程博客](https://engineering.classdojo.com/about/)） | 核心逻辑集中在 `ci-domain`，多端复用 |
| **Kahoot** | TypeScript 全栈（[技术博客](https://kahoot.com/tech-blog/)） | 我们用 Rust + 生成的 TS 类型达到同等"端到端类型安全" |
| **local-first（阿里云案例）** | 本地库 + 同步，离线可用（[文章](https://developer.aliyun.com/article/1755364)） | 教师机本地 SQLite + 局域网 WS 同步（保留） |

## 2. Crate 划分（依赖方向严格单向）

| Crate | 职责 | 依赖 | 现有资产 |
| --- | --- | --- | --- |
| `crates/ci-protocol` | 协议消息 enum/struct + 版本号 | 无 | `packages/protocol/messages.js`（转成 JSON Schema 后生成） |
| `crates/ci-domain` | 加权计分、题型权重、能力评价（雷达/评级/评语）、点名算法、课堂环节 | `ci-protocol` | `assets/js/{grade,analysis,rollcall,classroom}.js` |
| `crates/ci-store` | SQLite 读写、事务、备份/恢复、rev 单调 | `ci-domain` | `packages/db/schema.sql`（**直接复用，不改**） |
| `crates/ci-hub` | 房间状态机、WS 广播、HTTP API、过期写入 409、presence | `ci-store` | `sync-server.js` + `tests/hub-spec.test.js`（13 组场景） |
| `crates/ci-core` | 对外 facade：Tauri 命令 / axum 路由 / 启动编排 | `ci-hub` | `apps/teacher/src-tauri/src/lib.rs` |
| `apps/teacher/src-tauri` | 窗口、权限、sidecar（EasyTier）、命令注册 | `ci-core` | 现有工程 |
| `apps/student/src-tauri` | 同上（学生端） | `ci-core` | 现有工程 |

**规则**：展示层不得包含业务判断（例如"半对按 halfRatio 折算"必须调用 core）。若前端需要某个判断，就在 core 里加命令——这是防止规则再次分叉的唯一办法。

## 3. 跨语言类型：不手写

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| **specta + tauri-specta**（推荐） | 从 Rust 类型生成 TS 类型 + `invoke` 包装，Tauri v2 官方生态 | 命令签名改一次，前端类型自动更新；生态成熟 |
| ts-rs | 轻量，仅生成类型（不含调用包装） | 需要自己写 invoke 包装 |
| 手写 `.d.ts` | 零依赖 | 会漂移，本轮就要消灭的东西 |

选 **specta + tauri-specta**；`pnpm run gen:types` 生成到 `web/src/bindings/`（入库，便于前端独立开发，CI 校验是否最新）。

## 5. 关键设计决定（需要你确认）

1. **网页版（零构建静态页）何去何从**
   - 方案 A：保留为"轻量版"（教师临时借用电脑时用浏览器打开）→ 需要它也能连 Rust 枢纽（**协议不变，天然兼容**）
   - 方案 B：v5 稳定后退役，只留客户端
   - 我的建议：**A**（协议 v3 不变，保留成本低，且是很好的降级方案）
2. **Node 枢纽何时删**
   - 建议：Rust 枢纽通过全部一致性测试 + e2e 后**保留一个版本周期**作为参考实现，然后删（避免"一次删干净"导致无法回退）
3. **Android 学生端是否共用 `ci-core`**
   - 建议：共用（同一个 crate 编到 `aarch64-linux-android`），这样学生端也是"壳 + 展示"
4. **大屏**：作为独立小组件（Vue）跑在教师端窗口 or 独立浏览器（读同一枢纽）

### A.4 一致性基准（parity）—— 迁移期最重要的护栏

规则重写最容易出的不是"编译不过"，而是**边界差一点**：四舍五入、排序稳定性、评语措辞。
所以每迁一个模块都配一套"两边并行"的基准：

```
scripts/gen-parity-fixtures.mjs   用 JS 参考实现跑固定输入 → tests/fixtures/parity.json
crates/ci-domain/tests/parity.rs  用同一份输入跑 Rust 实现 → 逐字段断言相等
```

- 覆盖：能力评价 9 组（含"新手只有一道题"要判样本不足、综合分 70 这类边界）+ 判分 15 组
- 比对字段：overall / mastery / balance（null 也要一致）/ coverage / 评级 key+short+label /
  **评语全文** / 最强最弱轴 / 每条轴的 rate 与 correctRate；判分侧还有 expected、提交描述、自检告警
- CI 会校验基准是否过期（`npm run parity:check`）：JS 规则改了却没重新生成基准 → 直接红，
  免得回头误以为是 Rust 实现漂移
- 迁移完成后即使删掉 JS 实现，这份基准仍然有效（它就是"迁移后的回归依据"）

> 实测结果：`✅ 能力评价：9 组用例与 JS 参考实现逐字段一致`、
> `✅ 判分：15 组用例与 JS 参考实现逐字段一致`

### A.3 本轮踩到的两个坑（写下来免得再犯）

1. **Rust 的块注释可嵌套**：文档注释里写 `assets/js/*.js`，其中的 `/*` 会开一个永不闭合的嵌套注释，
   报错是 `unterminated block doc-comment`。文档注释统一用 `//!` / `///` 行注释。
2. **workspace 里的 profile 必须放根**：`apps/*/src-tauri/Cargo.toml` 里的 `[profile.release]`
   会被忽略（cargo 只警告不报错），已统一挪到根 `Cargo.toml`。
