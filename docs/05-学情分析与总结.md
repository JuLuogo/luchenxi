# 05 · 学情分析与总结

> 计算逻辑全部在 `assets/js/analysis.js`（纯函数，可在 Node 中直接测试），界面在 `assets/js/analysis-ui.js`。统计口径与加分口径保持一致，避免"分析说得好、分数却不高"的割裂。

## 1. 需求对应

> "根据每个人答对了多少、什么种类的题进行分析，分析哪方面不足，然后给一个总结。"

系统提供三层输出：

| 层级 | 产物 | 入口 |
| --- | --- | --- |
| 数据层 | 每人 × 每题型 / 每知识点的作答数、正确数、得分、得分率 | 学情页签表格 |
| 判定层 | 薄弱题型、优势题型、综合评定等级 | 自动计算（阈值可配） |
| 文本层 | 个人总结 + 班级小结（可直接复制到家长群/教研记录） | 「生成学情总结」 |

## 2. 指标口径（先看这张表，再看代码）

设某范围内计入口径的流水集合为 $R$：

| 指标 | 公式 | 代码 |
| --- | --- | --- |
| `attempts` 作答次数 | $\lvert R \rvert$（含跳过） | `analysis.js:30` `addToBucket` |
| `correct` 答对数 | 判定为 `correct` 的条数 | 同上 |
| `half` 部分正确 | 判定为 `half` 的条数 | 同上 |
| `wrong` / `skip` | 答错 / 跳过条数 | 同上 |
| `earned` 得分 | $\sum r.points$ | 同上 |
| `base` 满分基准 | $\sum r.base$ | 同上 |
| `correctRate` 严格正确率 | $correct / attempts$ | `analysis.js:40` `finalizeBucket` |
| `creditRate` **加权得分率** | $(correct + half \times halfRatio) / attempts$ | 同上 |
| `earnRate` 实得率 | $earned / base$（受抢答加分、答错扣分影响） | 同上 |

**哪些流水计入统计**（`analysis.js:20` `counts`）：

1. 必须是"可计数流水"：`tier` 非空且 `result !== 'manual'`（`store.js:489` `isCountable`）；
2. 若设置 `quickCountsAsAttempt === false`，则 `source === 'quick'` 的快捷加分只加分、不进正确率分母。

因此：**手动 ±分、归零抵冲不计入统计**；**跳过计入分母**（点了名没答出来也是一种学情证据）；**快捷题型加分默认计入**（老师按题型按钮 = 该题答对一次）。

### 2.1 多端提交对学情的影响

v3 的学生端提交与老师点名/手动判定**共用同一套统计口径**：两者都落成结构相同的积分流水，只是 `source` 不同（学生端为 `'student'`，`classroom.js:169`；字段定义见 `store.js:206`），所以不需要第二套指标，`analysis.js` 的 `counts()` / `studentStats()` 原样适用。

| 环节 | 代码 | 对学情的影响 |
| --- | --- | --- |
| 学生提交 → 流水 | `classroom.js:169` `recordResult({ …, source:'student' })` | 与点名/手动判定一样是"可计数流水"，直接进入 `attempts` / `correct` / `creditRate` / `earnRate` / `rank` 等指标 |
| 客观题自动判分 | `grade.js:98` `auto()` | 选择题：选项集合完全一致 → `correct`；提交是答案的**真子集**（漏选但没错选）→ `half`（按 `halfRatio` 计分，默认 0.5，`store.js:133`）；否则 `wrong`。填空题：全半角/空白/标点/大小写归一化后比对（`grade.js:57`，多种等价写法由 `grade.js:73` 拆分）→ `correct` / `wrong` |
| 空提交 | `grade.js:103` | 记 `skip`：**进分母、不计分**，与"点名答不出来"同口径，会拉低 `creditRate` |
| 主观题 | `grade.js:101` 返回 `null` → `classroom.js:152-167` 进「待确认」队列 | **老师判定前不产生任何流水**，因此未判定的提交完全不出现在学情里（不在分子、也不在分母）；老师点「答对/部分对/答错/跳过」后才按 `source='student'` 写流水（`classroom.js:210`），此刻才进入统计；点「丢弃」（`classroom.js:237`）则始终不留痕 |
| 抢答 | `classroom.js:77` `addBuzz()` 只写 `state.classroom.buzz` 与实时流 | 抢答本身**不加分、不进统计**；加分仍靠随后的作答判定或老师点名 |
| 学生端 / 大屏看到的统计 | 快照里的 `students[]` 只带轻量字段（`sync.js:258-268`） | 大屏个人榜（`index.html:226`）与学生端「本组 / 我的」看板（`student.js:326`、`student.js:353`）只能看到 `score` `attempts` `correct` `creditRate` `correctRate` `rank` `level` `rolls` `weakTiers`；**每题型矩阵、知识点短板、总结文案、CSV 等完整分析仍然只在教师端「⑤ 学情分析」**由 `analysis.js` 现算 |

由此带来三个可观察现象：

1. 学生一提交客观题，教师端⑤的作答数与得分率**立刻**变化（流水当场写入，随后 400ms 节流推给大屏与学生端）；
2. 主观题躺在「待确认」里时，⑤中**看不到**这条提交，老师也就不会"提前"把它算进薄弱判定；
3. 大屏/学生端的数字是**快照时刻**的统计（可能比教师端晚几百毫秒），教师端始终是权威口径。

自测：`npm run test:e2e:class`（真实枢纽 + 教师端 + 学生端，覆盖入座 → 开放作答 → 提交 → 自动判分 → 抢答 → 主观题待确认 → 教师判定 → dump 恢复）。

## 3. 薄弱 / 优势判定

```
对每个题型 t：
  若 t.attempts < settings.minSample（默认 2）        → 不下结论（样本不足）
  否则 若 t.creditRate <  settings.weakThreshold×100 → 薄弱
       若 t.creditRate >= settings.strongThreshold×100 → 优势
       其余                                         → 达标
```

实现：`analysis.js:62` `studentStats()` 中的 `weak` / `strong` 数组（按得分率升序，`weak[0]` 最弱）。

**综合评定等级**（`analysis.js:149` `levelOf`）：

| 条件 | 等级 | 颜色 |
| --- | --- | --- |
| `attempts < minSample` | 样本不足 | `#90a4ae` |
| 无薄弱题型且整体得分率 ≥ 85% | 优秀 | `#43a047` |
| 无薄弱题型 | 良好 | `#7cb342` |
| 薄弱题型 ≥ 2 个 | 需重点关注 | `#ef6c00` |
| 薄弱题型 1 个 | 有待提升 | `#fb8c00` |

> 阈值都在「题库与题型 → 计分口径设置」里改（`settings.weakThreshold` / `strongThreshold` / `minSample`），改完立即重算（见 [02 §4](02-数据模型与存储.md)）。

## 4. 知识点维度

题目的 `tags` 会在作答时通过 `qid` 反查（`analysis.js:62` 中的 `tagMap`）：

- 没有 `tags` 的题归入 `未标注`；
- 知识点短板判定仅用于文字总结：`attempts ≥ 2` 且 `creditRate < weakThreshold`，取最差的 3 个（`analysis.js:282` 附近）；
- 目前**没有独立知识点表**，靠字符串匹配，改名需同步题目（见 [09 已知限制](09-路线图与变更记录.md)）。

## 5. 文字总结

### 5.1 个人总结 `summarizeStudent(state, sid)`（`analysis.js:282`）

输出结构：`{ title, lines[], text, stats }`，`text = lines.join('\n')`。模板：

```
【张三 · 红队】当前积分 46 分，综合评定：良好
· 共作答 12 题：答对 8、部分正确 2、答错 1、跳过 1；严格正确率 66.7%，加权得分率 75%
· 基础题：作答 6 题，正确 5 题（部分正确 1），加权得分率 91.7%（+18 分），掌握扎实
· 拔高题：作答 4 题，正确 1 题，加权得分率 25%（+5 分），明显薄弱
· 优势题型：基础题
· 薄弱题型：拔高题
· 知识点短板：函数与导数(33.3%)
· 课堂参与：被点名 5 次
· 教学建议：建议按「拔高题」专项补练，先做 2～3 道同类题并及时讲评；错题与跳过共 2 题，建议课后复盘订正
```

规则细节：

- 无任何作答时，只输出一句提示（并说明被点名次数）；
- 逐题型的分档文案：≥85% 掌握扎实 / ≥70% 基本掌握 / ≥60% 仍需巩固 / <60% 明显薄弱（`analysis.js:266` `tierLine`）；
- 建议由多段拼装，按需触发（`opts.suggestion !== false` 时才生成）。

```
· 表现突出：张三（46 分，得分率 75%）…
```

### 6.1 按题目正确率（课后讲评的依据）

题型维度回答"这类题掌握得怎么样"，**题目维度回答"哪几道题要重讲"** —— 后者才是下节课的直接依据。

- `analysis.questionStats(state, quizId)`：按题目聚合作答数 / 答对 / 半对 / 答错 / 跳过 /
  正确率 / 掌握度（半对按 `halfRatio` 折算）/ 平均分 / **答错与跳过的人名**；
  排序按正确率升序（同率则作答多的在前）。只统计**有题目归属**的流水（快捷记分不计入）；
  题被删了也能统计（显示"题目已删除"，因为流水还在）。
- `analysis.questionReviewLine(stats)`：一句话结论，例如
  「本套题共 5 道有作答，整体正确率 62%。最需要讲评的是「…」（正确率 20%，5 人作答，4 人答错或跳过）；
  掌握最好的是「…」（正确率 100%）。另有 1 道题无人答对，建议课堂重讲。」
- 三处接入：**学情分析页**（`analysisQuestions` 表）、**课后学情总结**（`summarizeClass` 多一段
  题目维度结论 + 「讲评顺序建议」）、**大屏点评环节**（meta 快照带 `hardestQuestions`，
  大屏显示「📌 讲评建议」面板）。
- Rust 侧同口径实现在 `crates/ci-domain/src/question_stats.rs`，与 JS 逐字段 parity 比对。

## 8. 性能说明

- `studentStats` 每次会对全部流水做一次过滤（`recordsOf` → `allRecords`），`classStats`/`ranking` 会对每个学生各调用一次 —— 复杂度 O(学生数 × 流水数)。
- 课堂规模（≤ 60 人、≤ 数千条流水）无感知；若未来流水破万，应改为一次性遍历聚合（见 [09 路线图](09-路线图与变更记录.md)）。
- 界面渲染有 30ms 防抖（`admin.js:519` `scheduleRender`），连续记分不会卡顿；学生端提交触发的重渲染同样合并在这 30ms 里。

```powershell
node tests/logic.test.js     # 含学情口径、薄弱识别、CSV、总结文案的断言（第 6 组「学情分析」）
```
